# 🚀 Deploying the TenantPro Backend

This guide takes the backend from your laptop to a permanent public URL so the
Android app can reach it from anywhere. Recommended stack (all have free tiers):

| Piece            | Provider              | Why |
|------------------|-----------------------|-----|
| API hosting      | **Render**            | Free Node web service, deploys from GitHub |
| MySQL database   | **Aiven for MySQL**   | Free managed MySQL (Render has no MySQL) |

> Prefer everything in one place? **Railway** hosts both the Node app and a
> MySQL plugin — see the alternative at the bottom.

---

## Step 1 — Create a cloud MySQL database (Aiven)

1. Sign up at [aiven.io](https://aiven.io) and create a **MySQL** service (free plan).
2. Once it's running, open the service and copy the **Connection information**:
   - Host, Port, User, Password, Database name.
3. Load your schema into it. From your laptop:
   ```bash
   mysql -h <AIVEN_HOST> -P <AIVEN_PORT> -u <AIVEN_USER> -p <AIVEN_DB> \
         --ssl-mode=REQUIRED < tenantpro_db.sql
   ```
   (Aiven requires SSL — that's what `--ssl-mode=REQUIRED` is for.)

## Step 2 — Deploy the API to Render

1. Push this repo to GitHub (already done).
2. Go to [render.com](https://render.com) → **New +** → **Blueprint**.
3. Connect the `Tenant-Pro` repo. Render detects `render.yaml` and shows the
   `tenantpro-backend` service.
4. Render will prompt for the env vars marked `sync: false`. Fill them from Step 1:

   | Variable | Value |
   |----------|-------|
   | `DB_HOST` | Aiven host |
   | `DB_PORT` | Aiven port |
   | `DB_USER` | Aiven user |
   | `DB_PASSWORD` | Aiven password |
   | `DB_NAME` | Aiven database name |
   | `DB_SSL` | `true` (already set in the blueprint) |
   | `BASE_URL` | leave blank for now, fill after first deploy |
   | `BREVO_API_KEY` | email over HTTPS — see the note below |
   | `MAIL_FROM` | the sender address you verified with the provider |
   | `TWILIO_*` | optional (blank = mock mode) |
   | `JWT_SECRET` | auto-generated by Render |

5. Click **Apply**. Render builds and deploys. You'll get a URL like
   `https://tenantpro-backend.onrender.com`.
6. Copy that URL into the `BASE_URL` env var (Render → service → Environment)
   and save — the service redeploys.
7. Verify: open the URL in a browser. You should see
   **"TenantPro Backend is running!"**

### Email: use the HTTPS API, not SMTP

**Render's free web services block outbound traffic to SMTP ports (25, 465, 587).**
On that plan a Gmail or SMTP setup does not fail with a bad-password error — it
fails with a *connection timeout*, because the packets never leave the host. No
app password fixes it. `/healthz` reports this case as `UNREACHABLE` rather than
blaming the credentials.

So mail goes out over HTTPS instead, which is never blocked. Set **one** API key:

| Provider | Free tier | Domain needed? | Env var |
|---|---|---|---|
| **Brevo** | 300 emails/day | **No** — verify a single sender address | `BREVO_API_KEY` |
| Resend | 3,000/month | Yes | `RESEND_API_KEY` |
| SendGrid | 100/day | Yes | `SENDGRID_API_KEY` |

Start with **Brevo**: it is the only one that lets you verify a single *sender
address* rather than requiring a domain you own.

1. Create a Brevo account → **Senders & IPs** → verify the address you want mail
   to come from (a Gmail address is fine to begin with).
2. **SMTP & API → API keys** → create a v3 key.
3. On Render set `BREVO_API_KEY` to that key, and `MAIL_FROM` to the address you
   verified in step 1. Save — the service redeploys.
4. Check `/healthz`. `mail` should read
   `api:brevo (verified, sending as a****b@example.com)`.

**Switching provider later** (e.g. to something built for far higher volume) is a
config change, not a code change: set the new provider's key, and set
`MAIL_PROVIDER` to `brevo` / `resend` / `sendgrid` while both keys are present so
the cutover is explicit. An HTTPS key always wins over the SMTP variables.

Adding a provider that is not in the table above is one entry in
`backend/config/mailProviders.js` — nothing else in the codebase needs to change.

If you later move to a **paid** Render instance, ports 465/587 open up and the
`SMTP_*` / `EMAIL_*` variables work as a fallback. Port 25 stays blocked on every
plan. Note that Gmail is a poor transactional sender either way — it gets
rate-limited and spam-foldered — so the HTTPS provider remains the better choice.

## Step 3 — Point the mobile app at the deployed backend

In `mobile/.env`:
```env
EXPO_PUBLIC_API_URL=https://tenantpro-backend.onrender.com
```
Then rebuild the Android APK (`eas build -p android --profile preview`). The
installed app now talks to your live backend from any network.

## 🖼️ Image uploads: use Cloudinary in production

The app saves uploaded photos (profiles, property/room images, QR codes). On
Render's free tier the local filesystem is **ephemeral** — anything saved to
disk is wiped on every redeploy. To keep images permanently, the backend has
built-in **Cloudinary** support that turns on automatically when configured.

1. Create a free account at [cloudinary.com](https://cloudinary.com).
2. On the dashboard, copy the **`CLOUDINARY_URL`** (looks like
   `cloudinary://<api_key>:<api_secret>@<cloud_name>`).
3. Add it as an env var on your host (Render → service → Environment):
   ```
   CLOUDINARY_URL=cloudinary://123456789:abcdefg@your-cloud-name
   ```
4. Redeploy. On boot you'll see `🖼️  Uploads: Cloudinary mode` in the logs, and
   new uploads will return permanent `https://res.cloudinary.com/...` URLs.

Leave `CLOUDINARY_URL` blank locally to keep using the local `uploads/` folder —
no code changes needed to switch between the two. (The mobile app already
handles both absolute Cloudinary URLs and local `/uploads/...` paths.)

> Images uploaded **before** enabling Cloudinary still point at the old local
> paths and won't survive a redeploy — only uploads made after switching are
> permanent.

## 🔒 Production hardening (already wired up)
- The `/api/test-cron` route is now **automatically disabled** when
  `NODE_ENV=production` (which `render.yaml` sets).
- CORS can be restricted by setting `CORS_ORIGIN` to a comma-separated
  allowlist; left blank it stays open (fine for the mobile app).

## Alternative: all-in-one on Railway

1. [railway.app](https://railway.app) → **New Project** → **Deploy from GitHub**.
2. Set the service **Root Directory** to `backend`.
3. Add a **MySQL** database plugin to the project.
4. In the backend service **Variables**, reference the MySQL plugin values
   (`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`) plus `DB_SSL=true`,
   `JWT_SECRET`, `EMAIL_*`, `BASE_URL`, and the optional `TWILIO_*`.
5. Import the schema into the Railway MySQL (use its connect command), then
   deploy. Use the generated public domain as your `EXPO_PUBLIC_API_URL`.
